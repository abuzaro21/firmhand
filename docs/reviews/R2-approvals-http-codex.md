Four defects found. Verified with in-memory SQLite and direct HTTP-handler probes; no files were written and no sockets were opened.

1. **Medium — Purchase approval survives a newly required reserve override.** [src/commands.ts:291](../../src/commands.ts#L291) binds only the PO version, although the approval displays cash and budget evidence. Reproduced: approve a $1,560 PO showing $4,900 cash and $3,340 remaining; autonomously fund another $900 PO; execute the approved purchase. It commits with **$2,440 remaining**, below the $3,000 reserve, without asking permission for that newly required override. The PO version and hash still match. **Minimal fix:** revalidate the authorization context and require fresh approval when execution introduces an additional threshold override.

2. **Medium — Stale approval execution strands the request instead of replanning.** [src/kernel.ts:203](../../src/kernel.ts#L203), [src/agents/sales.ts:101](../../src/agents/sales.ts#L101). Reproduced: create the big-discount request, pause Sales, approve it, advance beyond its TTL, resume Sales, then tick. Execution correctly rejects the expired approval, but the lead remains `new` indefinitely with no quote or pending-agent memory. Sales deletes that memory before attempting execution. Furthermore, `ApprovalStale` is addressed to Sales but [src/kernel.ts:51](../../src/kernel.ts#L51) filters out delivery to the emitting actor, so **no stale task reaches Sales**. Finance has the same premature deletion pattern. **Minimal fix:** handle the rejected/stale execution result immediately using the retained request, applying the fallback or creating a fresh proposal before deleting its memory.

3. **Medium — Concurrent session creation defeats the company cap.** [src/server.ts:97](../../src/server.ts#L97). Counting companies and creating one are separate asynchronous operations. Concurrent requests can all observe spare capacity and then all insert companies. Reproduced with `maxCompanies: 1`: **eight parallel session requests returned 200 and created eight companies**. The default 400-company limit has the same race, weakening the advertised resource bound on the free host. **Minimal fix:** serialize admission through creation; for multiple processes, enforce the reservation transactionally in the shared database.

4. **Medium — A rate-limited reset deletes the existing company.** [src/server.ts:95](../../src/server.ts#L95). Reset drops the current company before checking the creation quota. Reproduced with `companiesPerMinute: 1`: create a session, then reset using its cookie. Reset returns **429**, but the company is already gone and the cookie resolves to nothing. The default configuration reproduces this after exhausting its ten-creation allowance. **Minimal fix:** check admission before deletion and preserve the existing company until its replacement succeeds.
